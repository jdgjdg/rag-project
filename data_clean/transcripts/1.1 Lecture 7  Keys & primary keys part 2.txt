**Super Keys and Keys**

We've previously seen the definition of a super key. While it is useful in and of itself, we are usually more interested in using it as a stepping stone towards the definition of a key.

What is a key? Also known as a candidate key, this is a minimal super key. In other words, no subset is also a key.

Let's return to our example. For instance, Net ID by itself is a super key. Net ID, classification, and birth date is also a super key. We've also stated that putting all attributes together is a super key.

Out of these, which is a key or a candidate key? Which of these is minimal? Net ID alone is minimal. You cannot have any subset of just Net ID that is also a key because you can't get any smaller than that one attribute.

In our other example, where we needed the combination of both attributes to be the super key, we discussed that neither attribute by itself was a key, and thus the combination was the only key.

Students are sometimes still confused about the differences between a super key and a key. They are, in fact, very similar. We can have multiple super keys and multiple keys. The purpose is that either a key or a super key determines the values of all other attributes. The real difference is that keys are subsets of super keys; in particular, they are the minimal subsets of the super keys.

**Super Keys and Tables with Duplicates**

There is a very important detail here. I've restated the definition for a super key: it's a set of attributes such that if the tuples have the same super key values, then the rest of the tuples are the same as well.

What if we're looking at tables instead of relations? What's different? Tables allow duplicate tuples.

When do we want to say that tuples are the same? There are two definitions of "the same" that we could consider. You could say they are the same if they look alike, or you could say they are the same only when they are essentially the same row. The defined choice is that we will only say tuples are the same when they are the exact same tuple, the exact same row.

If you think about that in context with the super key definition, it means if you have the same super key values (which two duplicates are going to have), then that determines which tuple you're looking at. But it doesn't, because in this case, you have a duplicate. What that means is if you have duplicate tuples, your table does not have a super key or a key. This is one of the results.

**Primary Keys**

We also define a primary key. When we have multiple keys, or even just one key, a primary key is one key chosen from all of those keys. We designate one of them as the primary key.

Why? If you're only looking at relations, the theoretical model, you don't care about primary keys. Primary keys are treated no differently than any other key.

However, in tables, in the actual database, primary keys have special meaning. They are used as the primary way to identify the tuple you are interested in. A primary key uniquely determines the rest of the tuple. Furthermore, they are frequently used in a special way in the implementation for looking up that tuple. The table is typically stored in a way that uses that primary key specially for that lookup.

In our schema syntax, for notation, we designate the primary key by underlining it.

Furthermore, in database systems, we use keys as constraints. You can designate a primary key or other key as a constraint that will be checked by the database system. In particular, every key has to be unique; it cannot occur in any other tuple. This is something the system will actually check and enforce. If you ever try to break that property, it will be disallowed in the system.
