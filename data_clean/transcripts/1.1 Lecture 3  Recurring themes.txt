## Recurring Themes in Database Design

### 1. Indexing vs. Search

Search is straightforward: we have data and typically perform a linear search. Indexing involves using a data structure which helps us find the data that we want, and we can find it more quickly than doing a search. The problem, or rather a trade-off, is that if we do have an index, it requires time to create and maintain this extra data structure.

### 2. Structured vs. Less Structured Design

Another recurring idea is that when designing a database, we can either have it more or less structured. What do I mean? Let me give you an example.

A more structured design might be like a spreadsheet where we have multiple pages and multiple tables, and each piece of data has a specific place where it belongs. In contrast, a much less structured version would be to throw all of our data into a single flat text file, where the data could be anywhere.

The big question here, another way of thinking about it, is how much of the data semantics – the meaning, the ideas that we want to specify about our data – are enforced by its structure.

#### Advantages of More Structured Design:
If we have a more structured design, it's easier to maintain data integrity. These ideas include what we know about the data, and constraints about making sure that we have the correct data in the correct place. It often means that we have less time needed for accessing this data. For example, we'll typically use some indexing.

#### Advantages of Less Structured Design:
A less structured design, however, does have advantages. It requires less time to implement because we don't have to think about the design nearly as much. As such, it's easier to understand because there aren't so many pieces to the design, and data can be placed wherever desired. More significantly, it's more flexible to change. Over time, we want to be able to change our design or program to allow more features. Our specifications are typically going to change over time. This is easier to do when we haven't made everything exactly tailored to our existing data.

### 3. Data Integrity vs. Flexibility

Another way to express the same concept is to flip this around and focus on the distinction between data integrity versus flexibility.

#### Data Integrity:
Data integrity is valuable because it can enforce constraints on data. It helps with planning. As mentioned, it often makes things faster, but more importantly, it helps maintain correctness in our database.

#### Flexibility:
Flexibility is valuable because our specifications change, and when that happens, we need to change our design along with them if we've tailored it to the original data.

Throughout this course, look for these recurring ideas and how they apply in different contexts.
