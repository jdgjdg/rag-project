We are modeling the idea of home properties in a typical suburban model.  The basic idea is that a house is built on a lot of land.  Lots are grouped into a block, which is usually the traditional idea of a city block, i.e., the land encircled by streets.  Blocks are grouped into a subdivision, which is typically developed all at one time.  A more detailed explanation is at https://en.wikipedia.org/wiki/Lot_and_block_survey_systemLinks to an external site..

We are using the following schema that is based upon the information used by the local Harris County Appraisal District, http://hcad.org/Links to an external site..  Homes and land are appraised periodically, meaning that their values are estimated so that they can be taxed.  The county is also subdivided into facets, i.e., sections of the overall regional map.  The facet that (the majority of) the lot occurs on is recorded for that lot.

ETL (Extract-Transform-Load)
Extraction is loading the data from its original source, in this case downloading it from a website into a GEDCOM or CSV file.
Transform is getting the data ready for the database.  This can either be done by code in either the application or the database or it can be done "by hand", modifying the source data file.
Load is getting the data into the database.  This will be done by application code calling your database API code.
If the transform is in the application, then we have the following data flow:

(Application) For each data item read from source ...
(Application) Transform that data item
(Application) Call API to send transformed data to database.
(Database) API code stores the result into tables.
If the transform is in the database, then we have the following data flow:

(Application) For each data item read from source ...
(Application) Call API to send untransformed data to database.
(Database) API code transforms data.
(Database) API code stores the transformed data into tables.
If the transform is by hand, then we have the following data flow:

(You) Modify the source file data.
(Application) For each data item read from source ...
(Application) Call API to send transformed data to database.
(Database) API code stores the transformed data into tables.
The following are the kinds of transformations that are the most likely in this assignment.

Completing incomplete dates -- e.g., "1900" into "1/1/1900".  This is discussed more in the "Dates" section below.
Splitting names -- e.g., "John David Greiner" into "John", "David", "Greiner".  This is discussed more in the "Names" section below.
Fixing misspellings.  This is discussed more in the "Names" section below.
Filling in missing data with NULL.
Removing unexpected or unsupported characters.  This is discussed more in the "Application-Side Code" section below.
Dates
The start date for a person's name and gender should be their birth date, assuming that is known.  Note that partial dates like '1967' and '1967 February' are not supported by the DATE type.  As a workaround, it is acceptable to use the first day of the year or month, e.g., '1967 January 1' and '1967 February 1', respectively.  Changes dates in the data file like this is an example of a transformation that you may need to do.

Aside:  "Partial dates" are part of the ISO 8601 standard.  While programming languages typically use that standard, they generally don't support partial dates.  As an alternative, we could have used separate Year, Month, and Day fields or even just stored dates as a text field.  For this assignment, we won't deal with partial dates.

The Claims
We have seen examples where a query using EXISTS produces the same query plan as a query using IN.  However, there was a web site (still broken?  https://beginner-sql-tutorial.com/sql-query-tuning.htm) claiming the following:

Use operator EXISTS, IN and table joins appropriately in your query.

Usually IN has the slowest performance.

IN is efficient when most of the filter criteria is in the sub-query.

EXISTS is efficient when most of the filter criteria is in the main query.

For example: Write the query as

select * from product as p
where EXISTS (select * from order_items as o
              where o.product_id = p.product_id)
Instead of:

select * from product as p
where p.product_id IN (select o.product_id
                       from order_items as o)
Not explicitly stated on that page, but (b) would favor a query such as the following.

select * from product as p
where p.product_id IN (select o.product_id
                       from order_items as o
                       where o.product_quantity > 10 and p.product_type = "gizmo")
