Where would we like to have error checking code in our combined database and application. On the application side that's where your user interfaces and that should include any input validation. In addition we want to handle any errors raised by the database. This is going to be important security issue. As we talked about with SQL injection because if we don't handle those errors the end user might see some of the error messages that are raised by the database that expose the internal implementation Furthermore you can usually provide better feedback to the user from within the application because you have better formatting you know more about the user at this point. On the database side some errors are simply much easier to check and much more appropriate to check when you actually have all the data. So for example referential integrity requires actually having other tables and all of their data. And of course that's handled built in by the foreign keys. Furthermore the database is in charge of the data and so we're not going to trust that the application is doing all of the checks that Need to be done so we're going to duplicate all of the checks anyway to just be sure. Now the way that we're going to check for these errors in the database side is first and foremost the constraints. Secondly triggers is also important. But in our imperative code you also have traditional conditionals and exception handling. And of course we usually use logging to register everything and we can look for issues in those logs as well.
