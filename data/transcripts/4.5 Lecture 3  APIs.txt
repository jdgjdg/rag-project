How can we adapt that model to SQL and databases? There's really two approaches to this. One is using views and one is using functions. Either views or functions are this top layer, the notion of a public method, and everything else is going to be private that outside users can't directly access. With views, you make the views public, and all of your tables are going to be private. That makes everybody have to access your views, but via the views, either reading or writing to the views allows them to manipulate the data in the underlying tables. For functions, you can make the functions public and grant the functions access to the underlying tables, but the outside user can't access the tables themselves directly. Now, the basic trade off here is that views provide a simpler way to set things up. Functions give you more flexibility in the control that you have there. In particular, views only can control tables, whereas functions, you can control access to any of objects within a database, not just tables, but your triggers and your other functions, et cetera. You can do all sort of things. With either style of API, you can go in and change the underlying table definitions. And not actually change the API that other users actually see. Your definition of the view or definition of the function might have to change because the table has changed.
