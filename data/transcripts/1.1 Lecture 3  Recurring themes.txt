Continuing our course introduction, I would like to introduce a few recurring themes that you should be on the lookout for during the course. First, there's the idea of indexing versus search. What do I really mean? Search is pretty straightforward. We have some data, and we probably just do a linear search of this data. Indexing is when we have some a data structure out here, which helps us find the data that we want, and we can find it more quickly than doing a search. The problem or rather a trade off is that if we do have an index, it requires time to create and maintain this extra data structure. Another recurring idea is when we are designing a database, we can either have it more or less structured. So what do I mean? Let me give you an example. So a more structured design might be like a spreadsheet where we have multiple pages and multiple tables where each piece of data has a specific place where it belongs. In contrast, a much less structured version would be, let's just throw all of our data into a single flat text file, and the data could be anywhere. So the big question here, another way of thinking about it is, how much of the data semantics, the meaning, the ideas that we want to specify about our data are enforced by its structure. If we have a more structured design, well, it's easier to maintain data integrity. These ideas of what do we know about the data, constraints about making sure that we have the correct data in the correct place. It often means that we have less time needed for accessing this data. For example, we'll use some indexing typically. A less structured design, however, does have advantages. It requires less time to implement it because we certainly don't have to think about the design nearly as much. As such, in some sense, it's easier to understand because we don't have so many pieces to the design, and you can put data wherever you want. More significantly, it's more flexible to change. Over time, we want to be able to change our design, or change our program to allow more features. Our specifications are typically going to change over time. And that's easier to do when we haven't made everything exactly tailored to our existing data. Now, another way to say pretty much the same thing is to flip this around and focus on the distinction between data integrity versus flexibility. The data integrity is great because it can enforce constraints on data. It helps us do the planning. As I said it, it often makes things faster, but more importantly, it helps us maintain correctness in our database. Flexibility is great, because our specifications change and when that happens, we need to change our design along with it if we've tailored it to the original data. Throughout this course, look for some of these recurring ideas and how they apply in different contexts.
